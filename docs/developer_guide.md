# Developer Guide

Everything a contributor or maintainer needs that doesn't belong on the landing-page README: project layout, the full conditioning-vector spec, data recovery, testing, and contribution standards.

Production code in `src/enerdatasynth/` never imports from `data/research_history/pjm_load/` — that directory exists purely for provenance/reproducibility and is not part of the installed package.

## Conditioning Vector (23 dimensions)

The exact schema `data/preprocess.py` produces and the models consume:

| Variable | Encoding | Dim |
|---|---|---|
| month | one-hot | 12 |
| day of week | one-hot | 7 |
| holiday | binary | 1 |
| Tmax | z-score (°F) | 1 |
| Tmin | z-score (°F) | 1 |
| spread = max(load) − min(load) | z-score | 1 |

See [`docs/api_reference.md`](api_reference.md) for how `.set()` maps human-readable inputs onto this vector, and [`docs/architecture.md`](architecture.md) for the conditioning-encoding caveat (this one-hot scheme vs. the research lineage's raw encoding).

## Restoring `data/processed/pjm_load/` from Backup

If `data/processed/pjm_load/` ever gets corrupted by a bad re-run, restore it from the backup that `enerdatasynth preprocess` wrote (this only exists once you've run it on your own data):

```bash
cp -r data/processed/pjm_load_backup/. data/processed/pjm_load/
```

The backup is written once, immediately after preprocessing completes, and is never touched again by any other script — see `data/preprocess.py`'s `duplicate_processed_dir`.

## Testing

```bash
pytest tests/ -v                     # full suite, ~2-20s
pytest tests/test_public_api.py -v   # just the fluent SDK
```

Most tests use small synthetic arrays and run in ~2s with no dependency on the real dataset. A few (public API, one config regression test) exercise real artifacts already in this repo — the shipped checkpoints, the scaler file, real subprocess installs — and skip gracefully if those aren't present. No real data ships, so tests that need arrays (sampling, failure analysis) build small synthetic ones.

## Before Submitting a Change

1. Run the test suite: `pytest tests/ -v`.
2. If you changed a default hyperparameter or added a new architecture/schedule/calibration mode, cite the evidence (a results file, a report) the way [MIGRATION.md](../MIGRATION.md) does — this project's standard is "every default is backed by a specific number in a specific file," not "this seemed reasonable."
3. If you promote a `data/research_history/pjm_load/` script into `src/`, verify checkpoint/behavior compatibility explicitly where it matters — see [MIGRATION.md](../MIGRATION.md) §3 for the pattern (loading the actual legacy checkpoint with `strict=True`, confirming zero mismatched keys).
4. If you touched `pyproject.toml` or added new modules, rebuild and sanity-check packaging: `python -m build && twine check dist/*`, and ideally a real `pip install dist/*.whl` — see [`docs/packaging.md`](packaging.md) for why the editable install alone isn't sufficient verification.

## Reporting Issues

Known gaps and open questions are tracked in [MIGRATION.md](../MIGRATION.md) (especially "research code that still needs manual review" and "where the final implementation could not be determined with certainty") and the README's Roadmap, rather than duplicated here — check there first.
